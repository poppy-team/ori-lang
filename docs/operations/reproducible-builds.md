# Reproducible builds and provenance

A reproducible build allows an independent environment to rebuild equivalent Ori artifacts from the same declared source and inputs.

## Scope

Artifacts include:

- `ori` and `ori-lsp`;
- static runtime libraries;
- runtime cdylibs;
- `runtime-link.json`;
- generated headers and debug maps;
- standard-library source/documentation package;
- release archives and platform packages;
- editor extension artifacts.

Bit-for-bit reproducibility may be reached incrementally. Input and provenance reproducibility are required even before every artifact is byte-identical.

## Declared inputs

A release build records:

- source commit and tag;
- project version;
- native ABI version;
- Rust toolchain from `rust-toolchain.toml`;
- `compiler/Cargo.lock`;
- target triple;
- build profile and features;
- linker strategy and version;
- relevant environment variables;
- platform SDK/build-tool version;
- packaging script version;
- generated-source inputs;
- CI workflow/run identity.

Undeclared local paths or workspace fallbacks invalidate release reproducibility.

## Sources of nondeterminism

Review:

- timestamps in archives and binaries;
- absolute build/source paths;
- directory traversal order;
- hash-map iteration order;
- randomized temporary/object names;
- debug identifiers;
- linker build IDs and UUIDs;
- host architecture detection;
- locale and timezone;
- line endings and file modes;
- generated metadata ordering;
- dependency download state;
- concurrent build ordering.

Each source should be eliminated, normalized, or documented as a remaining variance.

For `ori-driver`, a Cargo build script applies the last matching
`--remap-path-prefix` from `CARGO_ENCODED_RUSTFLAGS` to the manifest path
embedded in the driver. This keeps a remapped release binary from recording
the original checkout directory through its development runtime and stdlib
lookup. For example, from the repository root:

```sh
RUSTFLAGS="--remap-path-prefix=$PWD=/ori-source" \
  cargo --manifest-path compiler/Cargo.toml build -p ori-driver --release --locked
```

The remapped path is used directly only while it resolves to a real driver
manifest. Otherwise, development lookup searches near the executable and
then the current directory. Packaged runtime and stdlib beside the executable
take precedence, and `ORI_REQUIRE_PACKAGED_RUNTIME=1` prevents fallback to
source-tree assets. This change alone does not establish bit-for-bit
reproducibility for the whole release matrix.

## Build environment

Use a documented clean environment with:

- pinned toolchain;
- locked dependencies;
- explicit target;
- controlled locale/timezone;
- no source-tree runtime/stdlib fallback during package smoke;
- known linker/platform tools;
- isolated output directory;
- network disabled after dependencies are materialized where practical.

Containers or declarative CI images may improve reproducibility but do not replace recording the underlying versions.

## Runtime artifacts

For each target:

- build staticlib and cdylib from the same source/inputs;
- record their hashes;
- validate exported symbols;
- validate `ORI_ABI_VERSION` and project version;
- generate deterministic `runtime-link.json`;
- reject machine-specific local paths;
- stage into a clean target directory.

## Standard library and examples

Package only declared stdlib sources, sidecars, and intended examples.

Validation should detect:

- untracked local files entering the package;
- generated docs that differ from compiler export;
- incorrect permissions/line endings;
- obsolete syntax;
- nondeterministic file order.

## Archive creation

Release archives should use:

- sorted file order;
- normalized timestamps where supported;
- normalized owners/groups;
- stable file modes;
- deterministic compression settings;
- a generated content manifest;
- checksums produced after final packaging.

Platform packages may contain unavoidable tool-specific metadata; document the variance and preserve provenance.

## Verification workflow

1. Check out the exact source commit.
2. Materialize locked dependencies.
3. Build in the documented clean environment.
4. Produce target artifacts and package.
5. Compare file inventory, metadata, and hashes with the official artifact.
6. Classify differences as expected variance or defect.
7. Store a signed/attested verification report when infrastructure permits.

## Provenance record

A provenance record should include:

```yaml
project: Ori
version: 0.3.8
abi: ori-native-abi-1
source_commit: <sha>
target: <triple>
toolchain: <rust-version>
lockfile_hash: <sha256>
workflow: <provider/run>
artifacts:
  - path: ori
    sha256: <hash>
```

The actual schema should be versioned and generated by release tooling.

## SBOM

A software bill of materials should cover:

- Rust crates and versions;
- bundled native libraries/tools;
- runtime and stdlib artifacts;
- license metadata;
- checksums;
- target/package relationship.

SBOM generation should use the locked dependency graph and release contents, not only the source repository.

## Signatures and attestations

Maturity targets:

- publish checksum manifest;
- sign checksum manifest or artifacts;
- use protected release identity/keys;
- publish build provenance/attestation;
- document user verification;
- rotate/revoke credentials through an incident procedure.

Signatures do not prove source quality. They prove artifact origin and integrity relative to a protected identity.

## Incremental and release builds

Release packages should not depend on stale incremental outputs.

Use clean or fully validated content-addressed artifacts. If incremental reuse is allowed in a release job, every cache key and input must be included in provenance and independently validated.

## CI gates

- metadata and version agreement;
- clean-tree/package inventory;
- deterministic generated docs/catalogs;
- runtime static/cdylib parity;
- checksum manifest generation;
- isolated smoke test;
- optional second-build comparison;
- dependency/license/advisory report;
- upload of provenance and SBOM artifacts.

## Completion criteria for OPS-REPRO-1

- documented clean build recipe for each supported target;
- deterministic package inventory;
- normalized archive metadata where practical;
- machine-readable provenance record;
- checksums for all release artifacts;
- SBOM generation;
- isolated rebuild comparison for at least the primary Linux target;
- documented remaining nondeterminism;
- public verification instructions.
